# Migration d'un écrivain SiYuan vers wiki_writer

## When to Use

Migrer un script d'écriture SiYuan (import_notes.py, desaturer_memoire.py, cron veille, script manuel) vers le module partagé `wiki_writer`, ou tester une telle migration sur notebook jetable avant toute exécution réelle. Pour la simple lecture/interrogation de l'API SiYuan, voir la skill `siyuan`.

Module partagé : `%LOCALAPPDATA%\hermes\data\siyuan\wiki_writer.py` (ajouter son dossier à `sys.path`, comme `laya_client.py`).

## API publique (ne lève jamais, retourne un dict)
- `create_doc(notebook_id, hpath, markdown, *, attrs=None, tags=None, auto_categorize=True, if_exists="skip", ecrivain="inconnu", categorie=None, dry_run=False)` → `{"ok","doc_id","categorie","source_categorie","skipped","raison"}`. Écrit `custom-ecrivain` + `custom-categorie` à chaque création. `if_exists="skip"` = idempotent ; `"overwrite"` = export Markdown de l'ancien dans `data\siyuan\backups\` PUIS suppression, sous verrou. `dry_run=True` = simule sans rien écrire.
- `append_block(doc_id, markdown, *, data_type="markdown", dry_run=False)` — ajoute un bloc.
- `set_attrs(doc_id, attrs, *, dry_run=False)` — pose des attributs `custom-*`.
- `acquire_lock(notebook_id, timeout=30)` — verrou `msvcrt.locking`, un fichier par notebook dans `data\siyuan\locks\` ; context manager ou None si timeout.

## Invariants de sécurité (ne pas les casser en migrant)
- Token lu dans le .env (`SIYUAN_TOKEN`), jamais loggé ni dans une exception ; toute sortie passe par `_masquer()`.
- HTTP 127.0.0.1 uniquement, timeout sur chaque appel.
- Anti-doublon : contrôle d'existence + création SOUS LE MÊME verrou (anti-TOCTOU).
- Chemin du .env surchargeable via `SIYUAN_ENV_PATH` (tests sans toucher au vrai .env).

## Procédure de migration
1. ANALYSE (lecture seule) : API utilisée, gestion des doublons, notebook cible, attributs, contenu statique/généré, et l'effet destructif RÉEL du mode remplacement (ex. un `--remplacer` qui efface tout le notebook et ne recrée que ses notes). Signaler tout changement de comportement — ne jamais préserver un bug destructif « par fidélité ». Inclure la RÉSURRECTION : un script qui génère des docs pour des entités supprimées (sites, projets archivés) les recrée au re-run.
2. GATE HPATH (avant d'écrire) : comparer les hpaths que le script GÉNÈRE aux hpaths RÉELS des docs existants via `listDocsByPath` (lecture seule). Toute divergence (accent, espace, casse) = doublon en production → s'arrêter et signaler avant d'écrire quoi que ce soit.
3. DÉCISIONS : mode normal = `if_exists="skip"` (idempotent) ; mode remplacement = `"overwrite"` PAR HPATH (jamais delete-all) ; `ecrivain="script:<nom>"` + `categorie` fixe (`auto_categorize=False` pour notebook fixe). Script multi-notebooks : résoudre nom→id via `lsNotebooks` (lecture seule, AUCUNE `createNotebook`) ; notebook absent = message clair + code de sortie 1. Section à désactiver → une constante de sections actives (réactivation = une ligne), ne pas modifier le fichier de données source. Liste blanche des notebooks cibles (nom → catégorie fixe) : notebook HORS LISTE = refus clair + code 1, distinct du cas « notebook absent ». Pour que le harness puisse viser un notebook jetable sans affaiblir la liste, prévoir un hook d'environnement ADDITIF **et PRÉFIXÉ** (ex. `PUBLIER_CATEGORIES_EXTRA="nom=cat;nom2=cat2"`, dont une entrée n'est prise en compte que si le nom commence par `zzz-test-`). Un hook seulement additif reste une porte ouverte sur un notebook réel ; un hook préfixé ne peut pas élargir la production. Tester les DEUX côtés : le refus SANS le hook, ET un hook pointant une entrée réelle (ex. `hermes-skills=media-video`) qui doit rester SANS EFFET (la catégorie de la table s'applique, et la sortie ne doit pas mentionner la valeur du hook). Existence = hpath (`if_exists="skip"`), complétée par un garde LECTURE SEULE sur le titre : si un doc du notebook porte déjà ce titre à un AUTRE hpath, ne rien créer + message clair + code 1 (recettes d'énumération sans SQL dans `references/api-lecture-seule.md`). Même hpath = `skip` + code 0 : c'est l'idempotence voulue, PAS le garde — le code non nul ne concerne QUE le titre présent à un AUTRE hpath. Un `deja present, ignore` (code 0) n'est donc pas un manquement : si la spec de l'étape attend un code non nul sur un titre déjà présent, c'est la spec qui est incohérente — signaler l'écart, ne pas changer le code de sortie pour la faire coller.
4. Backup du fichier canonique seulement (`<fichier>.bak.<ts>`). Ne pas toucher aux copies de doc ni au clone git — les lister « à resynchroniser ».
5. Réécrire : plus aucun HTTP/token/SQL direct, tout délégué à wiki_writer. Conserver l'interface CLI utile mais **retirer purement et simplement les options destructives** (`--remplacer`) — pas de variante cachée derrière un `--confirmer` : argument passé = message expliquant le retrait + code de sortie non nul. Ajouter `--dry` (MÊME nom que l'original) qui fait la SIMULATION COMPLÈTE (`dry_run=True` passé à `create_doc` dans la boucle), pas seulement l'affichage du plan : il doit annoncer doc par doc « deja present, ignore » / « a creer [dry] » et finir par `0 cree(s), N skip(s) [dry : rien ecrit]`. Un `--dry` qui ne liste que le plan oblige à rouvrir le script pour pouvoir citer la sortie en validation réelle. Pour les tests, `--notebook` accepte un NOM de notebook (résolu via `lsNotebooks`) quand le script cible des notebooks nommés — ça teste aussi le cas « notebook absent ».
6. Copier le contenu des notes VERBATIM : extraire la liste depuis le .bak via `ast.literal_eval` et la réembarquer — ne pas retranscrire à la main (emojis/caractères spéciaux se corrompent). Vérifier par hash de la SORTIE des fonctions de contenu (importer ancien + migré, hasher `doc_*` et listes statiques), pas par relecture à l'œil.
7. Test UNIQUEMENT sur notebook jetable, jamais les notebooks réels. Garder l'ancien et le nouveau côte à côte 1-2 semaines.
8. Script one-shot destructif qu'on ne veut PAS migrer (script d'audit daté qui supprime puis recrée, purge d'entités disparues) : NE PAS le migrer, le NEUTRALISER — backup `<fichier>.bak.<ts>` puis RENOMMAGE en `<fichier>.py.archive`. Préférer le renommage à un garde d'arrêt en tête de fichier : il supprime tout chemin d'exécution sous le nom connu, sans dépendre d'un garde qu'une édition ultérieure peut effacer ; rollback = renommer. Vérifier ensuite que le nom connu est absent, que `python <ancien nom>` échoue, et qu'aucun appel à l'API ne part. Les copies de doc et le clone git gardent l'ancien nom : les noter « à resynchroniser (avec renommage) ».
9. VALIDATION RÉELLE, bornée au `--dry` : une fois les tests jetables verts, valider sur un notebook RÉEL en ne lançant QUE `--dry` (jamais le mode normal). Prendre un snapshot AVANT/APRÈS des notebooks réels par couple (doc_id, hash de contenu) — pas seulement les comptes, un doc peut changer sans que le nombre bouge — plus SHA256 de `index.faiss`/`chunks.jsonl` et l'état de la tâche Reindex. Jouer DEUX cas : un titre NOUVEAU (attendu `a creer [dry]`, 0 écriture) et un titre DÉJÀ PRÉSENT d'un vrai doc (attendu `deja present, ignore`). Conclure explicitement : « validation réelle = --dry uniquement ; la voie création n'a été validée que sur notebooks jetables ».

## Variante : l'écrivain est une TÂCHE CRON, pas un script

Quand l'analyse (étape 1) ne trouve aucun fichier exécutable, l'écrivain est le JOB lui-même : son prompt demande à l'agent d'écrire via la skill `siyuan` (appels API improvisés à chaque run). Ne pas conclure « rien à migrer » — la migration consiste alors à faire écrire le job par un petit script `publier_<cible>.py` (même contrat que les autres : hpath + `if_exists="skip"`, `ecrivain="cron:<nom-du-job>"`, catégorie fixe, résolution du notebook en lecture seule), au lieu de laisser l'agent réinventer l'écriture.

Où lire l'état sans rien exécuter :
- `profiles\<profil>\cron\jobs.json` — prompt, `skills`, `model_snapshot`, `schedule`, `last_run_at`, `last_status`, `last_error`, `next_run_at`, `failure_streak`. Le prompt EST la spécification d'écriture en vigueur : c'est lui qu'on compare aux décisions de migration.
- `profiles\<profil>\cron\executions.db` — tables `executions` (statut et erreur par run) et `cron_incidents`. Donne le taux d'échec réel du job, invisible dans `jobs.json` qui n'en garde que le dernier.
- Les documents du notebook cible : un nom daté (`YYYY-MM-DD-…`) dit quels runs ont réellement produit quelque chose. Un run en échec ne laisse AUCUN document — c'est la preuve la plus directe, et un trou dans la série date l'échec.
- Le dossier `skills\` du profil : un profil a sa PROPRE copie des skills, qui peut être figée à une révision plus ancienne que celle du profil principal (comparer tailles et mtime). Le signaler comme point de maintenance — une migration du skill ne se propage pas toute seule.

Pièges propres à ce cas :
- **Aucun contrôle d'existence dans le prompt** : un nom daté ne protège que sur un autre jour, donc un re-run le même jour duplique. Vérifier dans le notebook si c'est déjà arrivé (deux docs au même titre) — c'est la preuve que le contrôle manque, à citer dans l'analyse.
- **Un job agent qui écrit des données a ses échecs dans `last_error`**, pas dans un log applicatif : « all targets were skipped by pre-dispatch filters », modèle/route indisponible, etc. Les relever : ils expliquent les dates manquantes dans le notebook et comptent autant que le contrôle d'existence dans le rapport.
- **`model: null` dans `jobs.json` = le job tourne sur le DÉFAUT DU PROFIL, pas sur son `model_snapshot`.** Le snapshot est figé à la création/dernière édition ; un run ultérieur suit `model.default` du profil. Observer le modèle RÉEL dans `state.db` du profil (`sessions.model` de la session `cron_<job_id>_<horodatage>`) et dans `cron/usage_audit.jsonl` (une ligne par tir : `model`, jetons, `error`, `duration_ms`) — conclure « le job tourne sur auto/best-reasoning » à partir du snapshot envoie toute l'analyse au mauvais endroit.

### Diagnostiquer un run en échec (lecture seule, avant toute migration)

1. `cron/output/<job_id>/<AAAAMMJJ_HH-MM-SS>.md` : le scheduler y écrit le prompt COMPLET, l'en-tête `FAILED` et la trace exacte, même quand la livraison Telegram a réussi. C'est la source la plus directe, à citer plutôt que le log applicatif.
2. `cron/executions.db` (`executions` : `status`, `error`, `delivery_outcome`, `scheduled_instant` ; `cron_incidents` : `state`, `alerted_at`) : `status=failed` + `delivery_outcome=delivered` coexistent — l'échec est celui du TRAVAIL, pas de l'envoi. Vérifier dans `jobs.json` si `last_run_at` colle à l'heure planifiée (run planifié) ou non (run manuel).
3. Le texte d'erreur `RuntimeError: …` vient de `cron/scheduler.py::_final_response_from_result`, qui lève quand l'agent n'a produit AUCUN message final : le run est classé `cron_incomplete_no_output`. Ne pas en déduire « la livraison a échoué » ni « le modèle est cassé » — lire la chaîne d'appels du run.
4. **Le job est un run d'AGENT avec les toolsets cron du profil** : prouver la disponibilité d'un outil par le résolveur, pas par lecture du config : `from hermes_cli.tools_config import _get_platform_tools; _get_platform_tools(cfg, "cron")` (à exécuter avec le python du venv Hermes). `platform_toolsets.<plateforme>` ne liste que des RESTRICTIONS par plateforme — son absence pour `cron` ne signifie pas « pas d'outil », et une restriction écrite pour `telegram` ne borne pas les runs cron. C'est ce contrôle qui décide si le plan « le job appellera un script » est viable.
5. **Le cron tourne DANS le processus gateway qui le tique** : la ligne `Cron scheduler will tick N profile(s): [...]` du `logs/gateway.log` (racine) nomme les profils servis, et l'outil terminal d'un run cron hérite de l'environnement de ce processus (seuls les secrets/credentials providers sont retirés du sous-processus, pas les variables système). Le lanceur (`gateway-service/Hermes_Gateway.vbs` → `wscript` → `tools/python-* -m hermes_cli.main gateway run`) pose `HERMES_HOME` sur la RACINE du home, jamais sur le dossier du profil : tout ce qui résout `%LOCALAPPDATA%\hermes` (le `.env` de `wiki_writer`, ses chemins de log et de verrous) tombe donc juste depuis un run cron d'un AUTRE profil. Ne pas conclure « le script ne trouvera pas son .env » sans avoir déroulé ces deux résolutions.
- **Un `auto/<canal>` (best-reasoning, best-free, best-chat…) n'est PAS un combo nommé** : il n'apparaît pas dans la table des combos du routeur, c'est un canal virtuel dont la liste de candidats est recalculée à chaque requête (étapes `virtual-auto-<canal>-N-<provider>` dans les call_logs). « Quelles cibles avait-il le jour D » n'est répondable que par la trace des tentatives : dire « introuvable » si l'historique est purgé, et décrire le pool par les étapes réellement tentées, jamais par la liste d'un autre jour. L'échec de classe est `all targets were skipped by pre-dispatch filters` ; le combo frère qui rend `No target in combo <X> supports tool calling; request carried N tools` prouve qu'un des filtres pré-envoi est la capacité d'appel d'outils.

## Harness de test jetable (reproductible)
- Notebook `zzz-test-*` créé par le setup, supprimé en `finally` ; un résiduel éventuel est détecté et supprimé au démarrage.
- Supprimer AUSSI le verrou du notebook jetable (`data\siyuan\locks\<notebook_id>.lock`) à sa suppression : `release()` déverrouille mais ne supprime pas le fichier, donc sans ça la vérification « locks/ propres » échoue en fin de harness (et le harness doit prendre le snapshot de `locks/` avant de commencer pour ne rapporter que SES résidus).
- Protection RAG idempotente : SHA256 (pas la taille) de `index.faiss` + `chunks.jsonl` avant/après ; mettre la tâche « Hermes - Reindex RAG » en pause SEULEMENT si elle est active, et restaurer exactement l'état trouvé (ne jamais forcer « activé »).
- **Fenêtre de tir** : toute passe qui touche les notebooks ou l'index se termine AVANT le run planifié de nuit (Reindex à 03:00 ici). Relever l'état de la tâche au début ET à la fin de chaque étape, et refuser de démarrer une étape qui chevaucherait la fenêtre : l'état attendu en fin d'étape est « Prêt » avec un `NextRunTime` dans le futur, c'est la preuve à citer. Un run nocturne manqué suivi d'un rafraîchissement manuel est invisible au contrôle de fraîcheur — sauf si l'identité du run (`LastRunTime` / `LastTaskResult`) est contrôlée, ce qui est un correctif à proposer, jamais à appliquer d'office.
- Compter les notebooks réels par SQL récursif (`SELECT id FROM blocks WHERE type='d' AND box='<id>'`), pas par filetree top-level — un doc en sous-dossier fausse le compte.
- Test du mode remplacement : peupler le jetable de N docs factices (dont les hpaths cibles à contenu factice) et vérifier que les N-2 autres survivent avec le MÊME doc_id ET le même hash de contenu.
- Asserter sur des VALEURS, pas sur des chaînes formatées : un `%s` sur un flottant rend `+0.2 $` et non `+0.20 $`, un test qui cherche la chaîne formatée échoue sur un script pourtant correct. Comparer au format réellement produit (ou au nombre), sinon on consomme un cycle à « corriger » un script sain.
- Contrôle « aucun chemin de production dans la copie de test » : comparer le LITTÉRAL exact (`pathlib.Path(r"<chemin prod>")` absent, `pathlib.Path(r"<chemin test>")` présent), jamais une sous-chaîne comme le nom d'utilisateur — le dossier de test vit lui-même sous le profil, donc un test du genre `"searc" not in contenu` est toujours faux.
- Deux échecs d'affilée d'un harness sur un script sain = suspecter le HARNESS d'abord : corriger le test, rejouer, et ne retenir un correctif de script que si l'échec persiste. Le rapporter comme tel (bug de test, pas de script).
- **Un cas « fichier absent » doit porter un nom VALIDE pour le script.** Le refus de nom (regex de titre) est évalué avant l'existence du fichier : un fixture nommé `inexistant-<date>-cible.md` teste le rejet du nom, jamais la branche `introuvable` — le test passe au vert sans avoir couvert ce qu'il annonce. Nommer le fixture exactement comme un cas légitime, puis le supprimer pour créer l'absence.
- **Asserter l'état EXACT du notebook jetable, pas un compte.** Le test du garde-titre crée un document PARENT de sous-dossier (ex. `/zzz-dossier/<titre>`) : la liste récursive rend alors le dossier ET ses enfants, donc une attente « il reste N docs » est fausse. Comparer la liste triée des noms attendus.
- **Le test « aucun appel destructif » se fait sur le fichier CANONIQUE : après toute édition de la copie de travail, re-copier vers le canonique et re-vérifier le SHA AVANT de lancer le harness.** Un `cp` oublié fait tester la révision précédente et le contrôle d'absence échoue (ou passe) pour la mauvaise raison. Corollaire : si le nom de l'API interdite doit être absent du fichier, il doit l'être aussi des commentaires et docstrings — reformuler le commentaire, jamais affaiblir le contrôle (`"removeDocByID" not in source` est binaire).

## Pièges
- **Jamais de secret dans une ligne de commande** (`grep <token>`, argument d'outil) : la ligne de commande est loggée. Le contrôle anti-fuite lit le token lui-même et n'affiche QUE des compteurs (fichiers scannés, occurrences).
- **`schtasks` sort en cp850 (codepage OEM), pas en UTF-16** : décoder cp850 en premier. Tenter `utf-16-le` d'abord « réussit » sur du texte ANSI et produit du charabia qui masque la vraie lecture de l'état de la tâche.
- **Comparer des hashes, pas des tailles** : une taille identique n'exclut pas un contenu modifié.
- **`createDocWithMd` ne round-trip pas** : `exportMdContent` renvoie un frontmatter YAML (`title`/`date`/`lastmod`), le titre du doc en H1, ET **deux espaces en fin de ligne** (sauts durs markdown). Comparer une note créée à sa source après normalisation, jamais par égalité stricte : retirer le bloc frontmatter, retirer la ligne `# <titre>`, puis `rstrip()` CHAQUE ligne avant de hasher. Sans le `rstrip` par ligne, un corps pourtant identique ressort avec +2 caractères par ligne (échec de test trompeur qui fait croire à une corruption d'accents). Pour du brut sans décoration : `POST /api/block/getBlockKramdown {"id": doc_id}` (annotations `{: id=… }` à retirer).
- **La normalisation d'export est ASYMÉTRIQUE : le source n'a ni frontmatter ni titre ajouté.** Un export porte DEUX lignes H1 quand le contenu commence lui-même par un `# …` : `# <nom du doc>` (ajouté par SiYuan, texte = le `title:` du frontmatter) PUIS le premier H1 du contenu. Une normalisation unique qui « retire la première ligne `# ` » sur les deux côtés supprime du VRAI contenu du source et fait échouer un round-trip pourtant intact. Écrire deux fonctions : côté source, `rstrip` par ligne ; côté export, retirer le frontmatter, puis la SEULE ligne égale à `# <title du frontmatter>`, puis les lignes vides de tête. C'est la symétrie qui doit être testée, pas la valeur d'un hash unique.
- **SiYuan re-écrit aussi les espaces INTERNES : `**  - ` devient `**   - `** (un espace ajouté, autour d'un gras suivi d'un tiret). Un hash strict diffère donc toujours sur cette ligne alors que le contenu est intact. Comparer le texte après réduction des suites d'espaces à un espace, et rapporter l'écart comme ce qu'il est : mise en forme normalisée, aucun caractère perdu (le prouver par le hash post-normalisation ET par le nombre de lignes différentes avant).
- **Contrôle d'existence par titre (SQL `content`) vs par hpath** : l'ancien contrôle par titre rate un doc dont le titre a divergé du hpath après un renommage et le recrée. `wiki_writer` contrôle par hpath (`listDocsByPath`) — c'est la bonne clé ; basculer toujours sur hpath en migrant.
- **`importlib.util.spec_from_file_location` renvoie `loader=None` sur un fichier .bak (extension non-.py)** : pour importer un module depuis un backup dans le test de contenu identique, utiliser `importlib.machinery.SourceFileLoader(name, path)` explicitement, puis `spec_from_loader`.
- **Lister les enfants d'un doc hiérarchique (`listDocsByPath`)** : le paramètre `path` attend le champ `path` du parent — son chemin `.sy` (`/2026….sy`) — PAS son hpath. `path="/<nom>"` renvoie `[]` SANS erreur, ce qui fait croire qu'un garde-titre est inutile et le désactive en silence ; le nombre d'enfants est `subFileCount` (champ tardif de l'item JSON, invisible sur une sortie tronquée).
- **Écrire le script canonique** : si `write_file` refuse (« stale_write_blocked », fichier lu en pagination), ne pas insister — écrire la nouvelle version dans un fichier de travail (`cache/scratch/…`) puis `cp` vers le chemin canonique, ou utiliser `patch` pour une édition ciblée ; re-vérifier `py_compile` + SHA après.
- **Tout écart mesuré se signale, jamais ne se corrige en silence** : quand un test révèle un comportement non anticipé de l'API (décoration d'export, forme d'un listing, panier de verrous), le rapporter dans le rapport d'étape avec le contournement retenu, et re-jouer le harness complet après le correctif (une modification pendant une étape de validation repasse par une étape de test).
