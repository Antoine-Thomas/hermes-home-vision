# Intégration MARI (.NET 8 / Orleans)

MARI (github.com/kaonomi-net/mari, MIT) est un framework d'orchestration multi-agents sur Microsoft Orleans : VGrains (grains virtuels = agents), Signaux (pub/sub), Portes (corrélation booléenne), Déclencheurs (Cron/Signal/Stream), Séquences (chaînes de VGrains). Tout est déclaratif : des définitions sérialisées JSON compilées par DefinitionCompiler.

## When to use

- Héberger un nœud MARI (NoCluster local) dans un processus ASP.NET Core (bridge REST).
- Définir et tester Signaux / Portes / Déclencheurs / Séquences.
- Exposer un pont entre un système externe (Python, Hermes) et les signaux MARI.
- Missions POC multi-phases sur MARI (audit puis intégration).

## Conduite de mission POC (exigence utilisateur)

Une phase = un rapport (≤ 30 lignes : ce qui a été fait / résultat mesuré / décision CONTINUER | RECODER | ABANDONNER) puis **STOP**. Ne JAMAIS enchaîner la phase suivante sans validation explicite de l'utilisateur (« OK phase suivante »). Un audit = lecture seule : aucun fichier modifié, aucun service démarré, aucun commit ; cloner dans un dossier isolé hors du runtime cible. Si une erreur bloquante apparaît : s'arrêter et demander l'arbitrage.

**Économie d'itérations (exigence utilisateur sur les phases de mesure)** : grouper les contrôles indépendants (ports, services, git) dans UNE commande shell ; ne pas relire les fichiers sources déjà lus ; ne pas relancer un test qui a déjà produit son résultat ; si un run de mesure meurt, diagnostiquer par le log du run et relancer, pas recommencer à zéro.

## Procédure

0. Avant tout protocole de masse (50+50) : passer un **E2E minimal** (2 signaux espacés de MOINS de la fenêtre — écart strictement inférieur, cf. pitfall ActiveWindowInterval — → 1 ligne journal attendue). Si 0 ligne : arrêter, ne pas lancer le protocole. Une seule tentative.
1. Cloner MARI dans un dossier isolé (hors runtime cible), commit figé, `git status` propre avant toute modification.
2. Installer le **SDK .NET 8** (`winget install Microsoft.DotNet.SDK.8`) — le runtime seul ne suffit pas : sans SDK 8, `dotnet build` d'un TFM net8.0 échoue (NU1100 targeting packs manquants), le SDK 10 ne peut pas le remplacer.
3. Créer le projet bridge : `dotnet new webapi --framework net8.0` — SANS `--framework`, le template génère net10.0 avec un package OpenApi dont la restauration échoue.
4. Hoster le nœud dans le même processus : `builder.Host.UseMARINode(...)` — recette complète dans `references/node-and-bridge-recipe.md`.
5. Piner les ports APRÈS UseMARINode (cf. pitfall NoCluster).
6. Définir le cas d'usage (Signal → Porte → Trigger → Séquence), enregistrer via `AddInMemoryDefinitionProvider`.
7. Exposer `POST /fire` et `GET /status`, tester E2E, mesurer (latence, corrélation, ports).

## Pitfalls

- **NoCluster() force les ports par défaut (11111/30000) et écrase la config JSON.** NoCluster enregistre `ClusterNodeEndPointOptions` (overrideValue=true) AVANT que l'auto-configurateur d'endpoints (overrideValue=false) ne tourne : celui-ci réutilise l'instance enregistrée et ignore la section `MARI:Endpoint`. La voie qui marche : `WizardConfig().SetupCluster(_ => { })` (PAS NoCluster) + `PostConfigure<EndpointOptions>` sur le host avec `o.SiloPort` / `o.GatewayPort` (les propriétés s'appellent **SiloPort/GatewayPort**, pas `Port`), `AdvertisedIPAddress = Loopback`, endpoints d'écoute à null. PostConfigure s'exécute en dernier et gagne. Vérifier par `netstat`, pas par le log « Initializing silo ».
- **Sans pin, les ports sont DYNAMIQUES** : l'auto-configurateur scanne 5000→65536 (`GetAndReservedNextUnusedPort`) et les daemons de code externe 30000→65536. Dans un environnement avec plage réservée (ex. Wazuh 54985-55084), un démarrage peut atterrir dedans → toujours piner explicitement et vérifier avant démarrage (`netsh int ipv4 show excludedportrange protocol=tcp`).
- **ISignalService.Fire rejette les reference types dans `data`** : `if (!type.IsValueType) throw new Exception()` dans SignalService. Passer `null` ou un struct. Pire : Fire est `[OneWay]` → l'exception est AVALÉE (aucun log, aucun déclenchement, HTTP 200 quand même). Pour diagnostiquer la résolution des définitions, utiliser un appel non-OneWay : `SubscribeAsync` ou un endpoint `/diag` qui subscribe par nom. SignalNotFoundException = définition absente ; `ArgumentException: GetGrainId has been called on an unexpected type` sur un receiver non-grain = le NOM est résolu (le receiver doit être un grain pour un vrai subscribe).
- **`ActiveWindowInterval` est une borne INCLUSIVE : deux signaux espacés d'exactement la fenêtre ne déclenchent PAS.** Vérifié : fenêtre 60 s, écart 60 s → 0 ligne (le 1er signal expire à la borne avant l'arrivée du 2e), écart 10 s → 1 ligne. Toute réduction de fenêtre pour accélérer un POC (ex. 300→60 s) invalide les protocoles calés sur l'ancienne valeur : l'écart entre signaux doit rester STRICTEMENT inférieur à la fenêtre, et la purge entre itérations du harnais doit dépasser la fenêtre. Un E2E « qui marchait » qui échoue après réduction de fenêtre n'est pas une régression MARI — c'est l'écart devenu égal à la borne.
- **Une porte se subscribe par DoorId, pas par nom** : `SubscribeAsync("nom-de-porte")` lève SignalNotFoundException — comportement normal, une porte n'est pas un signal. `Trigger.Door(...)` crée le SignalTriggerDefinition avec `ListenDoor`.
- **UseMARINode sur un host existant IGNORE le setupConfig** : la surcharge `UseMARINode(host, setupConfig, builder)` ne fait rien du setupConfig (il n'est utilisé que par `MARINode.Create` qui construit son propre host). Charger la config par les sources du host (appsettings.json du WebApplicationBuilder) ou forcer en code (PostConfigure).
- **La séquence consomme le SignalMessage reçu** : SignalTriggerVGrain passe le signal reçu en input → `.RequiredInput<SignalMessage>()` ; ajouter `.Configure("...")` avant `.Call(...)` pour typer le contexte en `IExecutionContext<string>` (sinon erreur CS1503).
- **VGrain custom** : interface `: IVGrain` avec `[VGrainIdFormat(IdFormatTypeEnum.String, FirstParameterTemplate = "...")]`, classe `: VGrainBase<TInterface>, TInterface, IGrainWithStringKey` ; enregistrer via `.SetupNodeVGrains(cfg => cfg.Add<TInterface, TImpl>())`. Un VGrain N'EST PAS un builder de porte : `X.Create(...).UseLogicalAggregator(...)` n'existe pour AUCUN VGrain — ne jamais inventer une API ; recopier le modèle connu-bon d'un VGrain du même projet (ex. IJournalWriterVGrain/JournalWriterVGrain) pour une nouvelle séquence (interface + classe + `Sequence.Build(...).Use<TInterface>().Configure("id").Call(...)` + enregistrement dans `SetupNodeVGrains`). Vérifier la chaînabilité d'une API dans le source MARI (`IMARINodeVGrainWizard.Add` retourne le wizard) avant de l'utiliser.
- **Le processus bridge en arrière-plan verrouille bin/Debug/*.dll** : rebuild → MSB3027/MSB3021 (fichier utilisé par un autre processus). `taskkill /F /PID <pid>` (ou /IM Bridge.exe) avant `dotnet build`.
- **Lancer le bridge depuis bash : le binaire vit dans `bin/Debug/net8.0/Bridge.exe`, PAS à la racine du projet.** `./Bridge.exe` depuis `C:/mari-poc/bridge` répond « No such file or directory » alors que le build a réussi. La forme qui marche : `cmd /c "C:/mari-poc/bridge/bin/Debug/net8.0/Bridge.exe"` en `terminal(background=true)` — le `&` nu est rejeté par l'outil, et `Start-Process` n'existe pas dans le shell bash de l'agent (cmdlet PowerShell). Vérifier la montée par `netstat -ano | findstr "55551 55552 55553"` (3 ports en LISTENING) puis `curl http://127.0.0.1:55553/status` → 200 ; le log confirme « Now listening on: http://127.0.0.1:55553 ». Après `taskkill /F /PID`, l'exit code 1 du process est l'arrêt demandé, pas une erreur du bridge.
- **TypeNameHandling.All dans MARISerializer est un vecteur RCE** (TODO signalé dans le code) : la désérialisation Newtonsoft avec TypeNameHandling.All + binder permissif d'Orleans laisse le JSON stocké/distant choisir n'importe quel type chargeable. Restreindre à `TypeNameHandling.Auto` + un `ISerializationBinder` allow-list (types MARI./Orleans. uniquement) ; le binder retourne `null` pour les types hors liste → Newtonsoft lève une `JsonSerializationException` contrôlée (pas de crash silo). Test : désérialiser `{"$type":"System.Diagnostics.Process,..."}` doit lever, pas instancier.
- **Un run de mesure long doit être lancé par une TÂCHE PLANIFIÉE Windows, pas en arrière-plan de session** : un `background=true` meurt à la frontière de session (le log s'arrête après la 1re itération, le PID disparaît, le bridge reste UP), et un relaunch manuel crée un DEUXIÈME écrivain. La forme qui survit : `Register-ScheduledTask` (+ `Start-ScheduledTask`) avec `-ExecutionTimeLimit (New-TimeSpan -Hours 2)` et `-WorkingDirectory` — vérifier ensuite par `Get-ScheduledTask` (State Running) et `Get-CimInstance Win32_Process` (un seul PID). Vérifier la progression par le contenu du log du run (head), pas par le seul PID.
- - **Une tâche planifiée SANS redirection stdout perd TOUT le log du run.** `New-ScheduledTaskAction -Execute python.exe -Argument script.py` exécute sans console : les prints partent dans le vide, `RUN_PROTOCOL.log` reste absent alors que le run travaille — absence de log ≠ échec du run. Deux options : (a) le script écrit LUI-MÊME son fichier de résultats (pattern `measure_protocol.py` : dump JSON en fin de run) ; (b) envelopper l'action dans `cmd /c "python C:/...py > C:/...log 2>&1"`. Pour vérifier un run sans log : compter les lignes du journal produit (journal.log), pas le fichier de log du script.
- **Deux écrivains sur le même journal = résultats corrompus, pas un échec MARI.** Un protocole qui mesure par comptage de lignes de journal.log n'est PAS concurrent-safe : deux `run_protocol.py` en parallèle produisent des latences NÉGATIVES (une ligne écrite par l'autre processus, horodatée avant le POST #2) et des compteurs faux — le run « échoue à l'itération 1 » ou « réussit 50/50 » pour de mauvaises raisons. AVANT tout lancement, vérifier l'absence d'instance active : `Get-CimInstance Win32_Process -Filter "name like 'python%'" | Where-Object { $_.CommandLine -like '*run_protocol*' }` (voir `windows-path-handling` : `Get-Process .CommandLine` ne rend RIEN). Une latence négative dans le journal = écrivain concurrent, pas une anomalie de timing. **Le PID rendu par `background=true` est le wrapper bash/cmd, PAS le child python** : `taskkill /PID <wrapper>` tue le wrapper et laisse le child vivant ET écrivant — signature : deux séquences de « Cycle N » interlacées dans le même log (cycles 14-15 d'un ancien process mêlés aux cycles 1-2 du nouveau). Après tout kill, re-vérifier ZÉRO instance par la commande CIM (un seul PID affiché = le wrapper a été tué, le child est resté).
- **E2E manuel OK + harnais qui échoue = le harnais est en cause, pas MARI.** Diagnostiquer en isolation sans relire les sources : (A) bridge répond ? (B) version python ? (C) fire manuel 2 signaux → 1 ligne journal ? (D) parse du timestamp ISO en Python isolé ? Le parse `fromisoformat('...Z'.replace('Z','+00:00'))` accepte les 7 décimales — un échec de parse est rarement en cause. Si A/B/C/D passent, l'hypothèse restante est l'état de la porte (signaux résiduels dans la fenêtre ActiveWindowInterval des runs précédents) ou la concurrence d'écrivains — vider journal.log et repartir d'un état propre avant de conclure.
- **Wazuh ne se vérifie pas par un port HTTP deviné** : `curl https://localhost:55085/...` peut rendre 000 alors que Wazuh tourne — le dashboard n'écoute pas forcément le port supposé. Contrôle de non-régression fiable : le service Windows `Get-Service | Where-Object Name/DisplayName -like '*wazuh*'` (WazuhSvc = Running) ; la plage de ports réservée se vérifie par `netstat -ano | grep LISTENING` filtré sur la plage (doit être vide).
- **Mesurer la latence par le journal, pas par l'API** : le Fire est `[OneWay]` → le POST rend 200 immédiatement, la vraie latence signal→action se lit en pollant journal.log (nouvelle ligne horodatée ISO) moins l'instant du POST #2. Protocole réutilisable : `scripts/measure_protocol.py`.
- **Silo inactif > 15 min = grains collectés → POST /fire acceptés mais AVALÉS** : Orleans `GrainCollectionOptions.CollectionAge` par défaut 15:00 ; après ce délai sans activité, les grains (SignalHandler, Door, Trigger) sont collectés et un POST /fire rend toujours 200 mais le signal meurt (`Cannot address a message without a target` sur `ISignalReceiver.ReceiveSignalAsync` dans le log, séquence jamais démarrée). Vérifier : `grep -c "Start sequence" bridge.log` — un POST qui ne fait PAS croître ce compteur est mort. Si le bridge tourne depuis > 15 min sans test, il faut le redémarrer (silo frais) avant un run de mesure ; ne pas conclure à un bug MARI ni au watcher (diagnostic : POST manuels → `Start sequence` croît ? OUI = watcher en cause, NON = silo collecté).
